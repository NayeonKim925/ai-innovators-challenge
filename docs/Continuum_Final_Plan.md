## 1. 통합 결론과 제품 정의
두 기획의 핵심 방향은 같다. 팀원안은 기존 기존 제품명의 `Candidate–Evidence–Human Review`를 유지하면서 담당자 변경 전후의 조사 연속성으로 제품 목적을 전환한다. Continuum안은 이를 교대 현장의 `사전 점검–인계–인수 확인–조사 재개`로 구체화한다.

**Continuum은 미완료 설비 이상 Case에서 AI가 원인 후보와 근거를 정리하고, 작업자의 확인 결과·미확인 항목·담당자를 지속적으로 관리하여 다음 교대가 같은 조사 상태에서 업무를 이어가도록 돕는 AI 인수인계 워크스페이스다.**

제품의 목적은 제조 이상 대응 중 **shift handover 프로세스의 정보 전달과 업무 연속성을 개선하는 것**이다. 원인 후보 분석은 유지한다. 최종 가치의 중심을 ‘AI가 정답을 맞혔는가’에서 ‘다음 담당자가 근거와 불확실성을 이해하고 조사를 이어갈 수 있는가’로 이동한다.

| 구분 | 최종 합의안 |
|---|---|
| 첫 사용자 | 교대하는 생산설비 담당자·정비 담당자와 교대조 리더 |
| 도입 주체 가설 | 설비보전·생산운영 책임자, 현장 DX 조직. 실제 구매 의사는 인터뷰로 검증 |
| 첫 적용 범위 | 한 설비군에서 교대를 넘겨 계속되는 이상 조사. 공장 전체 일지·교육 서비스는 제외 |
| 기본 기능 | 원인 후보·근거, 조사 기록, 미확인 항목, 인계 검토, 인수 확인, Resume |
| 브랜드·코드 | 기획명 Continuum. 기존 기존 제품명 저장소·분석 모듈을 재사용하며 리브랜딩은 별도 결정 |

자료 범위: 사용자가 붙여준 Continuum 최종안, 앞서 대화에 붙여준 팀원의 ‘기존 제품명 방향성 피벗 정리’, 공개 근거 및 저장소 코드. 두 ChatGPT 대화 링크의 본문은 열리지 않아 링크 내부의 추가·변경 내용은 확인하지 못했다. 코드는 실행하거나 수정하지 않았으며, 현장 성능·실제 AWS 배포 검증을 수행한 것은 아니다.

## 2. 기획 배경과 검증할 페인포인트

| 근거 | 확인되는 문제 | 제품 설계에 반영 |
|---|---|---|
| HSE 공식 인수인계 가이드 [1] | 정확한 업무 정보 전달, 인계자 준비, 양방향 소통, 인수자의 교차 확인이 필요하다. 정비 작업의 전달 실패가 사고와 연결된 사례도 소개한다. | 보고서 생성에서 끝내지 않고 검토·질문·수락을 하나의 흐름으로 연결 |
| NIST 제조업체 사례, 2019 [2] | 같은 유압 누유가 서로 다른 비정형 표현으로 기록되어 반복 문제를 파악하기 어려웠다. | 자연어 원문을 보존하면서 설비·관측·작업·근거를 연결 |
| TrendMiner의 Umicore 사례, 2025 업데이트 [5] | 시계열의 운영 맥락 연결과 긴 인수인계가 과제였으며, 분석과 인수인계 통합이 도입되었다. | 센서 그래프와 현장 기록을 같은 Case에 연결. 동시에 경쟁 기능의 존재도 인정 |

이 자료는 문제의 존재와 설계 필요성을 뒷받침한다. 한국 CNC 현장의 2026년 발생 빈도·손실 규모나 Continuum의 효과까지 증명하지는 않는다.

**핵심 문제 정의:** 센서·알람·정비기록이 남아 있어도, ‘어떤 근거로 무엇을 의심했고 어디까지 확인했는가’는 다음 담당자가 다시 재구성해야 할 수 있다.

| 페인포인트 | Continuum가 바꾸는 것 | 추가 검증 |
|---|---|---|
| 이전 확인 내용을 찾기 어려움 | 완료한 확인과 원문 근거를 바로 조회 | 실제 재파악 시간과 불필요한 재점검 빈도 |
| 가설이 사실처럼 전달될 위험 | 후보·관측·사람의 판단을 분리 | 실제 교대 기록에서 의미 변형 사례 |
| 미확인 항목 또는 다음 담당자 누락 | Open Item·담당자·기한·보류 사유 유지 | 중요한 누락 항목과 현장 필수 규칙 |
| 설명·보고서 반복 작성 | Case에서 인계 자료와 재개 화면 생성 | 입력 부담 대비 절약되는 시간 |

도입 전 교대 담당자, 보전 담당자, 교대조 리더에게 실제 미완료 사건 한 건의 전달 과정을 보여 달라고 요청한다. ‘마지막으로 다시 물어본 내용’, ‘현재 사용하는 시스템’, ‘필수로 재확인하는 안전 항목’, ‘책임자 부재 시 처리’를 우선 확인한다. 교육 효과나 전문가 대체를 초기 구매 이유로 삼지 않는다.

## 3. 경쟁 제품과 차별화 가설
Honeywell은 공정정보·문제·작업계획·교대기록의 통합을, Innovapptive는 이월 이슈·인수 확인·ERP 작업 연결을 이미 제공한다. TrendMiner도 시계열과 맥락을 연결한 분석·인수인계 사례가 있다. 따라서 기존 제품을 ‘글만 저장하는 서비스’로 설명하지 않는다. [3][4][5]

**차별화 가설은 ‘AI 요약’이나 ‘멀티에이전트 수’가 아니라, 원인 후보별 근거·반대 근거·미확인 상태를 버전 있는 Case로 유지하고 인계 전후의 손실을 검사하는 조합이다.** 공개 자료만으로 독점 기능·세계 최초·우월성을 주장할 수 없다. 실제 경쟁 제품 데모와 동일 조건의 사용자 평가로 검증한다.

## 4. 핵심 기능과 운영 원칙

| 기능 | 사용자 경험 | 구현 원칙 |
|---|---|---|
| ① 원인 후보·근거 보드 | 현재 조사할 후보와 왜 제시됐는지 확인 | 기존 순위 계산 유지. 순위는 원인 확률이 아니며 LLM이 임의로 수치·후보를 덮어쓰지 않음 |
| ② 조사 기록·Evidence Timeline | 짧은 메모가 관측·판단·미확인·작업으로 정리됨 | 원문, 출처, 작성자, 시각, 적용 범위 보존. AI 추출은 변경 제안으로 검토 |
| ③ Open Item 추적 | 이미 확인한 것과 남은 항목·담당자를 구분 | 미실행·확인불가·기록 없음 구분. 응답 완료와 증거 확보는 별개 |
| ④ Handover Linter | 인계 전 누락·모순·담당 공백을 확인 | 필드·참조·버전은 코드 검사, 문장 의미 문제는 AI가 제안 |
| ⑤ Packet·인수 확인 | 인계자가 검토한 상태를 수락하거나 설명 요청 | Snapshot 버전 고정. 인수자가 보지 않은 변경은 재검토 |
| ⑥ Resume·Case Q&A | 변경점과 남은 항목부터 확인하고 조사를 계속 | 현재 상태는 DB 조회, ‘왜’는 근거 검색. 신규 인수자는 변경점뿐 아니라 전체 핵심 상태도 제공 |

### 반드시 바로잡을 네 가지
**미확인은 인계 실패가 아니다.** 미확인 항목이 있다는 이유로 인계를 막으면 미완료 사건을 전달한다는 목적에 어긋난다. 해당 항목·상태·담당·보류 사유를 명시해 넘긴다. 필수 담당자가 없거나 현재 상태가 기록되지 않은 경우에는 일반 완료 처리를 보류하고, 현장 규정에 따른 관리자 확인·예외 기록 경로를 제공한다.

**근거 확인은 원인 확정이 아니다.** 육안에서 손상이 보이지 않았다는 기록만으로 전체 기계적 원인을 배제하지 않는다. ‘정상’에는 무엇을 언제 어떤 범위에서 확인했는지를 붙인다. 후보 상태 변경에는 근거와 사람의 검토 또는 검증된 규칙이 필요하다.

**JSON 저장만으로 누락이 사라지지 않는다.** 잘못 추출된 내용도 구조화될 수 있다. 필수 상태는 템플릿으로 직접 출력하고, 원문 대조·참조 검증·전달 전후 Open Item 집합 비교·사람의 확인을 함께 적용한다.

**인수 수락·조사 종료·실제 수리 완료를 분리한다.** 인수는 전달된 상태를 확인했다는 뜻이다. 연구용 조사 Case가 닫혔다고 설비가 수리되었거나 안전하게 재가동할 수 있다는 뜻은 아니다. ‘점검 요청’은 ‘정비 완료’로, ‘재발 기록 없음’은 ‘재발 없음 확인’으로 변환하지 않는다.

### Linter 예시
`진동 상태 미확인`은 다음 담당자에게 전달할 항목이다. `해당 항목의 담당자 미지정`은 보완 요청이다. `미확인인데 요약에는 정상이라고 표기`는 상태 모순이다. `인계 후 새 관측 발생`은 Snapshot 갱신·재검토 사유다. 이 구분은 현장과 합의한 규칙으로 구현한다. 긴급 대응·법정 안전 절차·필수 대면 인계를 소프트웨어가 대체하지 않는다.

## 6. 상세 시나리오와 핵심 화면

| 단계 | 사용자·시스템 행동 | 남는 결과 |
|---|---|---|
| 1. 14:03 이상 Case 시작 | 원본 사건을 재생하고 명시한 시점까지 기존 분석 실행 | 동일 Case ID, 분석 Run, 실제 후보 신호와 Evidence ID |
| 2. 후보 조사 | A가 상위 후보의 근거를 열어 확인 | 후보의 관측 근거·문서 비교 요청. 물리적 고장명은 검증된 매핑이 있을 때만 표시 |
| 3. 짧은 기록 | A: ‘알람 이력과 추세 비교 완료. 현장 점검은 미실시. 다음 조에 전달 필요’ | AI가 초안을 구조화하고 A가 확인. 완료한 검토와 미실시 점검을 분리 |
| 4. 15:55 인계 점검 | Linter가 다음 담당자 누락과 현재 상태의 확인 시각 누락을 표시 | 미실시 점검은 유지. 담당자·상태 출처·시각을 보완 |
| 5. Packet 발행 | A가 특정 버전의 인계 자료 검토 후 발행 | 후보·근거·미확인·제약·담당자와 Snapshot ID 저장 |
| 6. B 검토·인수 | B가 ‘무엇이 남았나’, ‘왜 이 후보인가’를 확인하고 수락 | 수락자·시각·버전 기록. 신규 변경이 있으면 Delta 재검토 |
| 7. 16:20 같은 Case 재개 | B가 새 관측 또는 승인된 점검 결과 추가 | 과거 분석은 보존하고 필요 시 새 Run 추가. 기존 후보를 조용히 덮어쓰지 않음 |
| 8. 검토 또는 보류 | 권한 있는 담당자가 증거를 검토 | 조사 검토 완료 또는 추가 확인·보류. 실제 조치와 결과는 별도 근거로 기록 |

### Resume 화면 예시
```text
CNC-07 / 냉각계통 관련 이상 / Case FR-001

현재 상태: 조사 진행 중 · 최종 원인 미확정
이미 확인: 알람 이력, 선택 시점까지의 추세 비교
미확인: 현장 점검 결과
다음 담당: Shift B 담당자
제약: 현재 설비 상태와 작업 허가 정보는 원본 기록 확인

후보 1: 기존 분석 엔진이 제시한 실제 신호
근거: 분석 Run R1의 E1, E2
아직 필요한 정보: 담당자가 등록·승인한 추가 확인 항목

[근거 보기]  [설명 요청]  [인수 확인]  [조사 계속]
```

**RAG/Q&A의 질문:** ‘지금까지 무엇을 확인했나?’, ‘확인하지 못한 이유는?’, ‘이 후보의 지지·반대 근거는?’, ‘인계 후 달라진 것은?’, ‘과거 사건과 다른 조건은?’에 답한다. 작업 상태는 현재 DB에서, 판단 이유는 기록된 근거에서 조회한다. 근거가 없으면 ‘이유 미기록’으로 답하며 시니어의 생각을 만들어내지 않는다.

인수자가 부재하면 기존 담당 표시를 조용히 지우지 않고 교대조 리더에게 미수락을 표시한다. 소프트웨어 장애 시에는 기존 인계 절차를 수행한 뒤 처리 이력을 복구한다. 중복 점검을 줄이더라도 현장 SOP상 필수 재확인은 유지한다.

## 7. 제안 아키텍처
![Continuum 아키텍처](faultrelay_assets/FaultRelay_Architecture.png)

**기술적 중심은 ‘공유 Case State를 사용하는 역할별 AI 처리 + 결정론적 상태 엔진 + 사람의 승인’이다.** LLM은 자연어 해석·질의응답·초안을 돕고, 저장·책임자 변경·인수 수락·종료는 서버가 검증한다.

현재 코드의 LangGraph는 `validate_request → run_deterministic_analysis → evidence_check → assemble_review`의 고정 흐름이다. 이를 이미 여러 자율 LLM이 협업하는 시스템으로 발표하지 않는다. LangGraph 공식 문서도 고정 workflow와 동적으로 도구·절차를 선택하는 agent를 구분한다. [7][9]

## 8. 에이전트 역할과 상태 설계

| 모듈 | 입력 → 출력 | 현재/추가 및 권한 |
|---|---|---|
| Candidate Analysis | runtime 관측·cutoff → 후보 순위·근거 | 기존 결정론적 도구 재사용. LLM 자유 진단으로 교체하지 않음 |
| Context Structuring | 작업자 원문 → 관측·판단·Open Item 변경 제안 | 추가 LLM. 원문·출처 첨부, 검토 없이 중요한 상태를 확정하지 않음 |
| Continuity Review | Case Snapshot → 누락·모순·보완 질문 | 추가. 단순 필수 검사는 코드, 의미 검사는 LLM 보조 |
| Handover & Resume | 검토된 Snapshot·Delta → 인계 초안·Q&A | 추가. 필수 상태는 템플릿으로 출력, LLM 실패 시에도 인계 가능 |
| Case Memory Retrieval | 설비·사건·권한·시점 → 과거 근거 | 후속 검색 도구. 별도 자율 에이전트가 필수는 아님 |

‘멀티에이전트’는 구현 선택이며 제품 차별성의 증거가 아니다. MVP는 FastAPI 내부 모듈과 제한된 LangGraph로 구현한다. 나중에 독립 도구 선택이 실제로 필요한 역할만 에이전트로 확장한다.

### 저장 구조 제안
| 객체 | 저장해야 할 핵심 |
|---|---|
| Case / AnalysisRun | 변하지 않는 Case ID, 분석 이력 목록, 각 cutoff·알고리즘 버전 |
| Evidence / OperatorObservation | 원본 위치, 시간·확인 범위, 작성자, 실제/시뮬레이션/합성 출처 |
| HypothesisTrack | 분석 후보 참조, 지지·반대 근거, 사람의 판단 상태, 변경 이유 |
| OpenItem / Action | 미실행·확인불가·미기록 상태, 담당자, 기한·보류 이유, 확인 결과 |
| Handover | from/to, source_version, Snapshot, 검토·수락·예외 이력 |
| MachineState / Outcome | 설비 운전 상태의 출처·확인 시각, 조치 기록, 결과 관찰 기간. 조사 종료와 분리 |

`CaseStatus`와 `HandoverStatus`를 별도로 둔다. 조사 중인 Case도 인수 완료될 수 있다. 기존 `confirmed` 응답은 ‘근거 확인’ 의미를 유지한다. `task.completed`여도 응답이 `unavailable`이면 미확인 상태가 남는다. 후보 지지 여부와 원인 확정 여부 역시 별도 축으로 관리한다. [8]

중요 상태 변경은 `expected_version`과 권한 확인을 통과해야 한다. 두 교대가 동시에 수정하면 오래된 요청은 갱신 후 재검토한다. 에이전트는 DB의 권위 있는 상태를 직접 변경하지 않고 제안만 제출한다. 시간·출처·미확인·담당자 필드는 요약 결과에서 누락되지 않도록 코드 수준에서 비교한다.

## 9. 기존 코드에서 이어서 개발하는 방법
기준은 `main@faf2643`이다. 저장소에는 이미 Case, EvidenceTask, CaseEvent, version과 근거 확인·최종 검토 게이트가 있다. 따라서 상태 객체를 처음부터 다시 만드는 피벗이 아니다. 기존의 단일 분석 결과에 묶인 Case를 **여러 조사 Run과 여러 교대를 통과하는 Case**로 확장한다. [8][10]

| 기존 파일/영역 | 재사용할 것 | 새 기획을 위한 변경 제안 |
|---|---|---|
| `backend/app/domain.py` | Case·Task·Event·Review 계약 | 별도 Handover, OpenItem, OperatorObservation, HypothesisTrack; Case 담당·Run 참조 확장 |
| `backend/app/workflows/investigation.py` | 후보 계산·근거 검사 고정 흐름 | 분석 변경 최소화. 새 결과는 같은 Case의 새 Run으로 연결 |
| `backend/app/services/cases.py` | 근거 확인·재개·검토 게이트 | 같은 Case에서 관측·후속 Run 누적; 여러 필수 Task가 있을 때 전체 종료 조건 검증 |
| `backend/app/repositories/cases.py` | 저장소 경계·조건부 버전 쓰기 | Snapshot 및 담당자 보존. 규모 확장 시 전체 Scan 대신 설비·조직·담당자 인덱스, 이벤트 분리 |
| `backend/app/main.py` | Case API·보고서·조사별 chat | 관측 추가, Case 재분석, 인계 점검/발행/수락, Resume, Case별 Q&A 추가 |
| `frontend/src/App.tsx`, `api.ts` | Case Inbox·조사 화면·타입 계약 | 인계 검토·Resume 컴포넌트 추가; 미확인 상태·인수 버전·409 갱신 처리 |
| `frontend/server.mjs`, 테스트·문서 | 프록시·회귀 테스트·안전 경계 | 새 API allowlist, 권한·버전·인계 누락·동일 Case 재개 E2E 추가 |

파일별 근거: domain [8], workflow [9], case service [10], repository [11], API [12], frontend API [13], 팀 핸드오프 문서 [14].

### 우선 처리할 실제 구조 차이
현재 `InvestigationCase`는 `investigation_id` 하나를 가리키며, 추가 관측 후 기존 결과를 재순위화하지 않는다. `analysis_run_ids`와 현재 Run 참조를 추가해 동일 Case의 시간별 분석 이력을 연결한다. 기존 결과는 변경 불가로 유지한다. [8][10]

현재 서버에는 조건부 버전 저장이 있지만 요청 모델에는 화면이 본 `expected_version`이 없다. 인수 승인은 클라이언트가 확인한 Snapshot 버전까지 비교하도록 확장해야 한다. 역할명·작성자 문자열만으로 실제 사용자 권한을 검증했다고 보지 않는다. [8][11][12]

팀 문서상 실제 AWS 영속성·Guardrail·공개 배포 검증은 남아 있다. 기능 코드 존재와 운영 검증 완료를 구분한다. 현재 루트의 AgentCore 실험 경로를 운영 중 멀티에이전트로 주장하지 않는다. [14]

## 10. 데이터와 MVP 개발 순서

### 데이터 구성
**Machine Evidence:** causRCA 유지. 정상 운전 실측 데이터와 hardware-in-the-loop 고장 시뮬레이션을 구분한다. 전부 실제 현장 고장 이력이라고 설명하지 않는다. 데이터 기록 시각은 CNC가 값 변경을 발행한 시각이므로 신호 간 엄밀한 선후관계가 보장되는 것은 아니다. [6]

**Operational Layer:** 교대·메모·점검 응답·인계·수락은 합성 데모 데이터로 작성하되 `synthetic_demo` 출처를 표시한다. 원본 센서와 구분하고 근거 없는 ‘수리 완료’나 ‘재발 없음’을 실제 관측처럼 추가하지 않는다. 상대시간을 가상 교대 시각에 배치해도 원래 시간값을 보존한다.

**Evaluation Layer:** 정답 원인·진단 라벨은 오프라인 평가에만 사용한다. runtime API·프롬프트·검색 인덱스에서 제외한다. 개발 사례와 평가 사례를 분리하고, 이미 본 유사 실행이 성능을 부풀리지 않도록 시나리오 단위 분할을 검토한다. 기존 저장소의 runtime/evaluation 분리 원칙을 유지한다. [15]

### 구현 순서와 완료 기준
| 단계 | 개발 내용 | 완료 기준 |
|---|---|---|
| P0-1 상태 계약 | Case별 다중 Run, Handover·담당자·Open Item, 원본 출처 | 교대해도 Case ID 유지. 과거 분석·근거를 덮어쓰지 않음 |
| P0-2 인계 흐름 | 규칙 기반 사전 점검, Snapshot 발행·인수·설명 요청 | 미확인 항목 전달, 담당 공백 감지, 오래된 Snapshot 수락 방지 |
| P0-3 운영 화면 | 기존 Inbox/Workspace + Handover + Resume | A 기록 → B 수락 → 같은 Case 재개를 E2E로 시연 |
| P0-4 AI 보조 | 메모 구조화, 근거 인용 초안·Q&A | 추출 검토·참조 검사. LLM 실패 시 템플릿 인계 유지 |
| P0-5 검증·배포 | 영속성·권한·동시성·정답 누출·프롬프트 공격 테스트 | 핵심 회귀 통과와 실행 로그 확보. AWS 실검증 별도 완료 |
| P1 확장 | 과거 사례 RAG·실시간 연동·업종 어댑터 | 데이터·권한·현장 적합성을 검증한 기능부터 확대 |

**최소 데모:** 한 설비군, 한 이상 Case, 두 교대, 두세 개 후보, 여러 확인 항목 중 하나의 미확인, 담당자 누락 한 건, Snapshot 변경 한 건. 핵심은 화려한 에이전트 애니메이션이 아니라 다음 담당자가 같은 사건을 이어서 처리하는 장면이다.

MVP에서 하지 않는 것: 설비 제어, 자동 정비 지시, 모든 공장 시스템 동시 연동, 주니어 퀴즈·교육 모드, 검증되지 않은 고장 확률, 자동 수리 완료 선언.

## 11. 기대효과와 평가
다음 효과는 제품 가설이며 이미 달성한 성과가 아니다. 초기에는 복구 시간이나 다운타임보다 직접 측정 가능한 인계 품질과 상황 파악 시간을 검증한다.

| 기대효과 | 지표 | 측정 방법 |
|---|---|---|
| 다음 교대의 재파악 시간 감소 | Time-to-Context | 현재 상태·남은 항목·근거를 정확히 답할 때까지의 시간 |
| 중요한 미확인 항목 보존 | 중요 Open Item 누락률 | 사전 정의한 핵심 항목 중 전달·인식되지 않은 비율 |
| 가설의 사실화 억제 | 근거 없는 확정 진술률 | 원문/구조화 상태와 출력의 의미를 블라인드 검토 |
| 근거 기반 전달 | 인용 정확도·상태 추출 정확도 | 출처 ID 존재 여부뿐 아니라 해당 주장을 지지하는지 평가 |
| 담당 공백·오래된 수락 방지 | 미수락 항목·버전 충돌 처리 | 담당 누락, 동시 수정, 발행 후 변경 테스트 |
| 후보 분석 가치 유지 | Hit@k/MRR·판단 보류 적절성 | 정답 격리 상태에서 별도 오프라인 평가 |
| 현장 입력 부담 감소 | 기록·인계 준비 시간, 수정량 | 추가 입력에 드는 시간까지 포함한 사용자 테스트 |

**공정한 비교 설계:** 동일한 센서·알람·작업 기록으로 ‘기존형 구조화 일지 + 일반 AI 요약’과 Continuum를 비교한다. 원시 데이터만 제공하는 조건은 보조 기준으로만 둔다. 같은 모델·정보량을 유지하고 사례·노출 순서를 교차 배정한다. 현장 전문가가 없는 예비 테스트는 사용성·정보 보존 검증으로 한정한다.

질문 횟수와 재점검 횟수를 무조건 줄이는 것을 목표로 하지 않는다. 필요한 설명 요청과 SOP상 필수 재확인은 유지한다. 실제 MTTR·다운타임·비용 절감은 현장 파일럿의 후속 지표다.

## 12. 사업·서비스 확장성
첫 도입은 **한 설비군·한 교대 흐름에 읽기 전용으로 연결하는 파일럿**으로 제안한다. 기존 SCADA·Historian·CMMS를 대체하지 않고, 근거 링크와 조사 상태를 연결하는 보조 계층으로 시작한다. 생산운영·설비보전 책임자의 인계 품질 개선 요구와 IT/OT 담당자의 보안·연동 조건을 함께 확인한다.

확장은 같은 설비군에서 `교대 간 전달 → 운영자–정비팀 → 정비팀–엔지니어` 순으로 진행하고, 이후 다른 설비·사업장으로 넓힌다. CNC 검증만으로 화학·제약·반도체 공정 전체에 적용 가능하다고 주장하지 않는다. 업종별 용어·SOP·권한·작업허가·규제·데이터 어댑터 검증이 필요하다.

장기 자산은 채팅 대화량보다 **근거와 검토 이력이 연결된 Case, 일관된 상태 계약, 현장에 맞는 인계 규칙과 연동**이다. 이것이 쌓이면 과거 사건의 판단과 미확인까지 검색 가능한 Factory Investigation Memory로 발전할 수 있다. 지식 전승은 이 운영 흐름의 결과로 발생하며 교육 기능을 첫 제품으로 만들지 않는다.

**발표용 결론:** “Continuum은 AI가 원인 후보를 제시하는 데서 멈추지 않습니다. 어떤 근거가 확인됐고 무엇이 아직 미확인인지 추적해, 교대가 바뀌어도 같은 Case에서 조사를 이어가게 합니다.”
